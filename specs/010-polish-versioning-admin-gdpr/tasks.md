## Phase 3: User Story 1 — Safe evolution of the public API (P1) 🎯 MVP

**Goal**: a written policy, a decorator that signals deprecation in every response and in the
contract, a `410` after the removal date, a register that cannot drift from the code, a weekly
reminder, and a CI job that blocks unregistered breaking changes.

**Independent test**: a test-only view marked deprecated returns its normal body plus
`Deprecation`, `Sunset` and `Link` headers, is `deprecated: true` in the generated schema,
answers `410 endpoint_gone` after the sunset date; every other endpoint is unchanged
(`openapi.yaml` diff empty).

### Tests for User Story 1

- [ ] T006 [P] [US1] Write `backend/apps/common/tests/test_deprecation.py`: headers present on a test-only DRF view decorated with `@deprecated`; body and status unchanged; `Link` only when `successor` is given; `deprecated: true` and the removal date in the operation description of the schema generated by drf-spectacular; `410` with code `endpoint_gone` once the date has passed (freeze the date, no sleeping); a notice shorter than `API_DEPRECATION_MIN_NOTICE_DAYS` raises at decoration time; one structured log line `deprecated_call` per call with endpoint, client name/version from the `X-Client` header if present and request id, never user data; zero extra database queries (`django_assert_num_queries`)

## Phase 4: User Story 2 — Operator-only admin that cannot be abused (P2)

**Goal**: one admin site that only active operators reach, with TOTP in production, the API's
lockout, an optional IP allowlist, read-only final records, audited actions, and no sensitive
field on screen.

**Independent test**: each studio role is refused with 404; an operator without a valid code is

## Dependencies & execution order

- **Setup (T001–T003)** → **Foundational (T004–T005)** → stories.
- **US1** depends only on Foundational (T005 for the notice setting). T009 before T010; T014 before T015.
- **US2** depends on T004 (audit actions) and T005 (settings). T020 → T021 → T022 → T023 → T024–T028.
- **US3** depends on T004 only if it audits through new actions (it does not: `AuditEntry.Action.PRIVACY_EXPORT` already exists). T031 → T032 → T033; T035 after T033.
- **US4** depends on US1–US3 being done, because the README quotes their numbers and decisions.
- **Polish (T041–T051)** after the stories; ADRs and concept docs [P] among themselves.
- US1, US2 and US3 are independent of each other after Phase 2 and can be done in any order.

## Parallel examples

- US1: T006, T007, T008 together (separate test files); then T011, T012, T013 together while T009 is written.
- US2: T017, T018, T019 together; after T023, T024–T027 together (one `admin.py` per app).
- US3: T029 and T030 together; T031 first among the implementation tasks.
- Polish: T041–T045 together.

## Implementation strategy

1. **MVP = Setup + Foundational + US1**: the API has a policy and a working deprecation
   mechanism, proved by tests and by the contract diff. That alone protects the installed apps.
2. **Then US2** (largest security gain), **then US3** (legal completeness): one commit per
   coherent step, quality gate green after each.
3. **US4 last**, when the numbers are final.
4. Stop at each checkpoint and run the story's independent test before moving on.
